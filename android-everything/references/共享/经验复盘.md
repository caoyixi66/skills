# 经验复盘

## 什么值得沉淀

只记录已经验证、可重复使用的工程经验。

| 字段 | 内容 |
|---|---|
| 现象 | 哪条命令、日志或行为出现异常 |
| 直接原因 | 已被源码、日志或工具证实的触发点 |
| 安全做法 | 本次真实测试过的最小替代方案 |
| 验证证据 | 命令输出、日志、构建产物或设备行为 |
| 适用范围 | 机型、源码工作区、版本、模块 |
| 重新验证条件 | 哪些版本、路径或架构变化会使经验失效 |

## 归档位置

| 经验类型 | 写入位置 |
|---|---|
| 所有 Android 项目共用 | 对应 `共享/` 资料 |
| 某一机型或源码工作区专用 | 对应 `机型/<机型>/已知问题.md` |
| 某一机型的 framework、native、init、SELinux、内核、驱动、串口、崩溃或性能 | 先读 `机型/<机型>/技术专题索引.md`，再进入对应 `专题/` |
| 跨项目的终端、SSH、编码、构建环境或工具流程问题 | `共享/经验复盘.md`，必要时同时更新具体共享专题 |
| 强制工作边界 | 全局或项目 `AGENTS.md` |
| 一次性任务细节 | 当前任务记录，不进入 Skill |

## 问题记录门槛

任何源码、构建、终端、SSH、编码、设备、日志或工具问题都可以沉淀，但至少满足以下条件之一：

| 条件 | 记录方式 |
|---|---|
| 已定位首个决定性错误 | 写明现象、错误、证据和调查边界 |
| 已验证原因或可行替代方案 | 写明适用范围、风险和重新验证条件 |
| 可在多个任务复现的环境陷阱 | 写明触发条件和最小规避方式 |

不得将猜测、未复现问题、认证材料或个人敏感信息写入资料。一次性命令失误、无证据猜测或尚未区分根因与症状的异常，只保留在当前任务，不进入 Skill。

## GitLab Merge Discussion 自测试模板

需要为 Android 改动编写 GitLab 自测试说明时，优先使用“风险提示 + 独立场景 + 命令/预期结果 + 附件链接”的短模板：

1. 第一行写清测试前提，例如要求 `userdebug`、已刷入对应镜像，或会删除哪些真实数据。
2. 每个场景使用独立标题，按“执行命令 -> 必要设备操作 -> 预期标记”编号。不要在正文中写个人电脑路径、设备序列号或临时日志路径。
3. 把 `adb sideload` 传输完成与功能通过分开描述；以检查脚本的 `PASS` 标记、关键文件状态和 Recovery 日志作为功能判定。
4. 上传附件后再插入 GitLab 自动生成的 `[文件名](/uploads/...)` 链接。不要预造或猜测 upload ID。
5. 正文生成后明确列出需要用户手动 attach 的最小文件集合，不附带未参与当前测试的源码、未签名 OTA、构建中间产物或历史日志。

N6P `/private/config` 保护的当前最小附件集合为：

```text
prepare-private-config-protection-test.bat
check-private-config-protection-test.bat
N6Pro_ota_signed.zip
verify-private-config-recovery-edge-cases.bat
```

该方案的场景应包含：小数据量保护、超过阈值的 `/data` 备份、`data-marker` 启动恢复和 `directory-conflict` OTA 同名优先。当前不再使用 `force-data` 调试参数；大数据量场景使用 `over-50m` 真实创建 51 MiB 测试条目。

## GitLab 个人活动与工作回顾

GitLab 活动查询和 Markdown 工作回顾的完整流程见：

`references/共享/GitLab活动与工作回顾.md`

可复用的关键经验：

- 优先使用 API + Token；开始前确认 GitLab 地址、查询对象、Token 位置、时间范围、时区、活动类型、项目范围、去重规则、输出目录和格式要求。
- 先用当前 Token 验证账号身份，再分页读取活动；不能把未认证接口返回的公共数据当作个人记录。
- Push、Commit 和 Merge Request 是不同统计对象；Push 可能包含多个 Commit，MR closed 也不等于已合并，合并状态应读取 merged_at 和 merged_by。
- push -f 造成的同一逻辑修改按项目、分支、MR、标题和变更文件综合判断，报告默认保留最终工作结果，不把去重过程写成单独章节。
- Token、Cookie、密码和订阅令牌不得写入 Skill、报告或长期日志；原始 JSON、HTML、CSV 和调试文件默认放临时目录，最终只交付 Markdown。
- API 因权限、版本或网络不可用时，才回退到用户已经登录的 GitLab 页面；不导出 Cookie，也不把 Atom 最近少量记录当成完整时间范围。

## 浮点进度日志的科学计数法

| 字段 | 内容 |
|---|---|
| 现象 | Android `UpdateService` 的 logcat 进度可能输出 `progress=9.847642E-5`。 |
| 直接原因 | 浮点日志格式允许科学计数法；若正则只匹配 `[0-9.]+`，会截断为 `9.847642`，把实际的 `0.00009847642` 误报为超过 100%。 |
| 安全做法 | 解析进度时接受可带符号、指数部分的完整浮点格式，例如 `[-+0-9.eE]+`，再用支持科学计数法的浮点解析器转换后与 `1.0` 比较。 |
| 验证证据 | 2026-08-03 EF930 Update.apk OTA 日志中，按完整浮点格式统计 `206` 条状态回调，最大值为 `1.0`，大于 `1.0` 的数量为 `0`。 |
| 适用范围 | 所有依赖文本日志分析浮点进度的 Android、服务端或脚本工具。 |
| 重新验证条件 | 日志字段改为非浮点格式、统计工具更换语言/库，或引入 locale 相关格式后重新检查。 |

## 内存问题：将泄漏归属、内存压力与重启边界分开取证

| 字段 | 内容 |
|---|---|
| 现象 | CT20 2026-07-30 bugreport 同时出现 27 次 LMK kill、较高的 `report_monitor_service` RSS 和 native tombstone。 |
| 直接原因 | 这类证据能证明内存压力和进程崩溃，但单个 PSS/RSS 快照或 LMK 计数不能单独证明哪一个进程、哪个分配路径或哪一层内存是泄漏根因。 |

| 适用范围 | 所有 Android bugreport、native 服务、驱动/服务协作的内存问题。 |
| 重新验证条件 | 分配所有权、错误分支、Android 内存统计格式、进程重启机制或内核驱动实现变化后，重新采集同负载时间序列。 |

## EDK2 元数据：先验证当前工具链，再解释 DEC、INF、DSC、FDF

| 字段 | 内容 |
|---|---|
| 现象 | 容易把 DEC 的 `[Includes]`、DEC 的 `[LibraryClasses]`、INF 的 `[LibraryClasses]` 和 DSC 的 LibraryClass 映射混为同一个“依赖/链接规则”，进而误称 DEC `[LibraryClasses]` 是当前构建选择实现的必需步骤。 |
| 直接原因 | EDK2 元数据同名 section 分布在不同层级：DEC 描述 Package 公共接口，INF 描述模块需求，DSC 选择库实例，FDF 描述镜像布局。通用规范、工具检查和当前 BaseTools 实际 build 的行为不一定完全相同。 |
| 安全做法 | 先沿真实构建命令找到 `build -p <DSC>`，再分别核对消费者 INF、DSC 映射、提供者 INF 和 FDF。对 DEC `[LibraryClasses]` 必须直接查看当前 BaseTools 是否把它用于 build；不能仅凭通用 EDK2 概念下结论。 |
| 验证证据 | EF930 2026-08-17：`BaseTools/Source/Python/Workspace/DecBuildData.py:322` 注释 `not used in build at present`；普通链接路径由 INF `[LibraryClasses]`、DSC 的 `LibraryClass|Instance.inf`、提供者 INF 的 `LIBRARY_CLASS` 和 `[Sources]` 组成。ECC `Check.py:952-965` 可将 DEC 的 LibraryClass 作为元数据检查依据。 |
| 适用范围 | 使用 EDK2/UEFI 的 Android Bootloader、ABL、XBL 相关构建；结论优先适用于当前工具链版本，不自动外推到其他 EDK2 分支。 |
| 重新验证条件 | BaseTools、EDK2 分支、平台 DSC/FDF、构建包装脚本、静态检查配置或 LibraryClass 管理方式变化后，重新读取实际构建命令和工具源码。 |

## GPU/memtrack 统计与普通 statm/smaps 分开取证

| 字段 | 内容 |
|---|---|
| 现象 | 界面重绘后 `dumpsys meminfo` 的 GL/EGL mtrack 增长，但 `statm`/`VmRSS` 基本不变。 |
| 直接原因 | memtrack 统计 GPU/PVR/DMA-BUF 侧账目；`statm`/`smaps` 只统计 CPU 地址空间；framework 将 memtrack 数值复制到 PSS、RSS、Private Dirty 展示字段。 |

| 适用范围 | Android + PowerVR/IMG GPU；memleakd 如需覆盖应增加独立 GPU_ACCOUNTING_RISK。 |
| 重新验证条件 | memtrack HAL、PVR 驱动、framework 统计实现或 GPU 平台变化后重新采集同负载时间序列。 |

| 适用范围 | Windows 主机上的 Android ADB/Recovery 挂测、日志汇总、结果去重和受控清理。 |
| 重新验证条件 | ADB 版本、PowerShell 版本、脚本参数、Recovery 日志格式、输出目录、设备权限或清理保留策略变化后，重新执行语法/单元样例/目录边界验证，并至少做一轮真实设备验证。 |

## 辅助工具优先使用 Python

| 字段 | 内容 |
|---|---|
| 结论 | 对新的日志解析、CSV/JSON 汇总、路径边界检查、进程轮询和受控清理，默认优先使用 Python；PowerShell 只保留已有接口兼容或非常短的一次性命令。 |
| 原因 | Python 的 `pathlib.Path.resolve()`、`re.fullmatch()`、`csv`、`json` 和 `subprocess.run([...], shell=False)` 更容易显式区分设备路径/主机路径、避免 PowerShell `$Matches` 状态污染，并对删除范围做结构化校验。 |
| 安全做法 | 本机 Python 使用 `C:\Users\XGD\.codex\venvs\android-everything`，通过 `scripts/run-python.ps1` 入口运行；ADB 使用参数数组且不使用 `shell=True`；先写报告再删除；删除前后核对根目录 allowlist。Linux Android 源码、Git、构建、权限和远端日志仍必须由 Windows `pwsh` 通过 SSH 在 Linux 原生路径执行，不能因为改用 Python 而绕过 SSH 边界。 |
| 限制 | Python 只能减少脚本语言层面的错误，不能自动解决 ADB 时序、Recovery 重启、设备权限、USB 或文件系统问题；设备结论仍需实时日志和状态证据。 |
| 适用范围 | 新写的 Android 辅助工具、挂测控制器、日志解析器、统计报告器和一次性清理工具。 |
| 重新验证条件 | Python 版本、虚拟环境、依赖、ADB 参数协议或目标目录变化后，重新执行 `--help`、离线样例、路径越界样例和实际设备最小回归；不把临时 Python 脚本留在用户指定的清理目录。 |

## 跨基线移植：用 worktree 隔离脏工作区

| 字段 | 内容 |
|---|---|
| 现象 | Mino1 的 `A13/vendor/nexgo` 和 `A13/agenew` 工作区存在未提交 tracked 修改或 untracked 测试文件，同时需要从 `N82L-dev` 创建新分支并 cherry-pick memleakd 功能提交。直接切分支可能因为 `agenew/SystemConfig.mk` 等文件差异被 Git 拒绝，或在切换后把本地修改与 cherry-pick 混在一起。 |
| 直接原因 | 未提交修改属于原 worktree，不属于目标分支；如果目标分支或 cherry-pick 也修改同一路径，Git 无法无歧义地同时保留两边内容。worktree 能让原分支的脏文件和目标分支的干净文件位于不同工作目录。 |
| 安全做法 | 先对每个子仓库分别确认 Git root、remote、当前分支、目标分支 tip、dirty/untracked 状态。使用 `git worktree add -b cyx-n82l-memleakd <temporary-path> <target-base>` 从目标基线创建独立工作区，在临时 worktree 中 cherry-pick，推送后再用 `git worktree remove` 清理临时目录。原工作区保持原分支和原有未提交修改不变。 |
| 验证证据 | 2026-09-10 对四个仓库完成移植，源分支 `cyx-mino1-memleakd` 与目标分支 `cyx-n82l-memleakd` 的远端 tip 均通过 `git ls-remote` 核对一致：`A13_vendor_nexgo` 源 `92501c53`、N82L `c4fc88f4`；`A13_agenew` 源 `a491a7ec`、N82L `0487a772`；`A13_system_sepolicy` 源 `00006cd5`、N82L `ae3ac74a`；`PosSystemServiceV2` 源 `a283599f`、N82L `67ba8cb9`。 |
| 适用范围 | repo 管理的 Android 多仓工作区，尤其是需要从设备基线分支移植功能、同时保留当前工作区调试文件或测试工具的场景。 |
| 重新验证条件 | 目标远端、基线分支、worktree 支持、Git 版本、未提交文件路径或提交内容变化后，重新确认目标 tip、实际 cherry-pick diff 和原 worktree 状态；不能把历史提交 ID 当作当前事实。 |

## repo 软链接工作区的 root-owned object/ref 权限

| 字段 | 内容 |
|---|---|
| 现象 | 在 Linux 原生 repo 工作区中，`git add`/`git commit` 报 `insufficient permission for adding an object to repository database .git/objects`；`git fetch` 报无法更新 `refs/remotes/modules/...` 或无法追加 reflog。 |
| 直接原因 | 工作树 `.git/objects` 和 `.git/refs` 可能是指向 `.repo/project-objects/...` 或 `.repo/projects/...` 的软链接；其中部分前缀目录、ref 文件和 reflog 由 root 创建，而当前用户只能读取，不能在这些目录中创建 loose object 或 ref lock。 |
| 安全做法 | 先用 `git rev-parse --absolute-git-dir` 和 `realpath <gitdir>/objects`、`realpath <gitdir>/refs/...` 解析真实路径，并确认它们位于当前 repo 工作区的 `.repo` 下。只修复目标仓库真实 object/ref 路径中仍为 root 所有的条目，不递归修改整个 `.repo`。如果普通用户无法取得 root，可通过已配置的 Docker 以 root 仅对经过路径校验的目标目录执行 chown；之后重新运行只读状态检查和目标 Git 操作。 |
| 验证证据 | 2026-09-10 两个仓库分别出现 loose object 写入失败、remote-tracking ref 更新失败和 reflog lock 失败；解析真实路径后仅修复对应 `.repo` 下的 root-owned object/ref 条目，随后 amend、fetch、cherry-pick 和 push 均成功。 |
| 适用范围 | 使用 repo 符号链接 Git 工作树、共享构建账号或 Docker/root 混用产生对象目录属主不一致的 Android 源码工作区。 |
| 重新验证条件 | repo 工作区重新 sync、对象库迁移、共享账号或 Docker 挂载方式变化后，重新解析真实路径并确认属主；不得把一次 `chown` 结果无条件复用到其他项目。 |

## 长时间挂测与主要日志的默认输出位置
