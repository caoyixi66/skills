# GitLab 活动与工作回顾

## 适用范围

用于从 GitLab 查询个人或指定用户在一段时间内的 Push、Commit、Merge Request、合并和相关项目活动，并整理为便于同事阅读的 Markdown 工作回顾。

这是一套通用流程，不预设用户名、GitLab 地址、Token 文件位置、项目范围、日期范围或报告模板。

## 开始前必须确认

在发起查询或读取 Token 之前，先确认以下信息。能够从用户当前请求明确判断的字段可以复述确认，不要重复追问。

| 项目 | 需要确认的内容 |
|---|---|
| GitLab 地址 | GitLab 根地址，例如企业内网地址；不要把源码服务器地址误当成 GitLab 地址 |
| 查询对象 | 用户名、用户 ID，或 Token 对应的当前账号 |
| Token 位置 | Token 文件路径、环境变量名，或用户明确授权的其他安全读取方式 |
| 查询时间 | 开始日期、结束日期、时区；未指定时询问，不要擅自使用“最近一个月” |
| 活动范围 | Commit、Push、MR 创建/关闭/合并、评论、分支活动等需要统计哪些类型 |
| 项目范围 | 全部项目、指定群组、指定项目，还是仅与 Android 相关的项目 |
| 去重规则 | 是否合并 push -f 产生的重复提交、过程性提交、同一 MR 的多仓库提交 |
| 输出位置 | Markdown 保存目录和是否需要保留原始 JSON/CSV/HTML |
| 文档格式 | 是否有参考模板、标题语言、Summary/Notes 语言、字段顺序和排版要求 |

如果用户没有特殊要求，采用以下默认值：

- 使用 API + Token，查询 Token 对应账号。
- 时间范围使用用户给出的本地日期，按左闭右开区间过滤。
- 使用 GitLab API 获取活动，再用 Commit 和 MR 详情补充信息。
- 默认统计 Push、个人 Commit、MR 创建/关闭/合并；评论和分支活动只有在用户要求时加入。
- 同一项目、同一分支或同一 MR 下由 push -f 产生的同一修改只保留最终工作项，不把去重过程写进报告。
- 默认只交付一份 Markdown，不在目标目录留下抓取用 HTML、JSON、CSV 或调试文件。
- 默认文件名为当地日期的月日加 review.md，例如使用 MMDDreview.md 格式。
- 报告正文使用中文；每笔工作按项目、时间、问题点、解决方案、关键文件整理。
- 如果用户提供模板，模板优先级高于以上默认格式。

## Token 安全规则

Token 只用于当前查询，不得写入 Skill、报告、长期日志、截图、命令输出或提交记录。

优先顺序：

1. 用户已经提供环境变量名时，从环境变量读取。
2. 用户提供 Token 文件路径时，只读取文件内容，不回显内容。
3. 如果没有 Token 位置，先询问用户，不要猜测常见路径，也不要搜索整个磁盘。
4. 不把 Token 拼到 URL 查询参数中；使用 HTTP Header 传递。
5. 不导出浏览器 Cookie、密码或带 feed_token 的订阅地址作为替代认证材料。

在 Windows PowerShell 中，读取 Token 后应放入当前进程变量或内存对象，并避免将完整 Header、完整命令行和异常对象输出到终端。报告中只保留 GitLab 地址、用户名、项目、提交和 MR 链接等必要信息。

## 推荐查询顺序

### 1. 验证站点和账号

先发起只读请求确认 GitLab 可达，再使用当前 Token 请求当前用户信息。至少确认：

- GitLab 地址可访问。
- Token 有效且能访问 API。
- 返回的用户名和用户 ID 与查询对象一致。
- Token 具备读取活动、项目、提交和 MR 所需的权限。

认证失败时，停止继续统计并说明是地址、Token、权限还是接口响应问题。不要用未认证返回的公共数据冒充个人活动。

### 2. 获取活动索引

优先使用 GitLab Events API 获取时间范围内的活动索引，并完整处理分页。活动索引主要用于发现：

- Push 事件及其涉及的提交。
- Commit 事件。
- Merge Request 创建、关闭、更新或合并相关活动。
- 项目、分支和 Commit/MR 链接。

API 返回的时间通常是 UTC ISO 8601 格式。先解析为带时区的时间，再转换到用户指定时区过滤；不要直接按字符串比较本地时间。

分页必须持续到满足以下条件之一：

- 当前页为空。
- 返回数量小于 page size 且接口语义确认已经到末页。
- 下一页活动时间已经早于查询起点，并且已完成边界记录检查。

不能只读取第一页，也不能用 Atom 订阅的最近少量记录代替整段时间范围。

### 3. 补充 Commit 信息

对活动中发现的 Commit，补充读取以下字段：

- 完整 SHA 和短 SHA。
- 提交时间、作者、提交者。
- 项目和分支。
- 标题和正文。
- 父提交。
- 变更文件、增加/删除行数或 diff 摘要。

如果 GitLab 实例不支持按用户或时间直接列出全部 Commit，就以活动索引发现的 Commit 为主，再按项目详情补充，不能把项目默认分支的全部提交误认为用户提交。

### 4. 补充 Merge Request 信息

对活动中发现的 MR，读取详情确认：

- MR 编号、项目、标题、源分支和目标分支。
- 创建时间、关闭时间和合并时间。
- 合并人。
- 状态是 opened、closed、merged 还是其他状态。
- MR 中实际包含的提交和变更文件。

“MR opened”或“MR closed”只能说明状态操作，不能说明已经合并。是否合并以 MR 详情中的 merged_at 和 merged_by 为准。

如果用户要求统计“本月合入的 MR”，按 merged_at 过滤；如果要求统计“本月创建的 MR”，按 created_at 过滤，不能混用。

### 5. 关联 Push、Commit 和 MR

同一次 Push 可能包含多个 Commit。整理时按以下优先级建立关联：

1. Commit 或 MR 链接中的项目和分支。
2. Push 事件中的提交 SHA。
3. MR 详情中的 commit 列表。
4. 标题、时间和变更文件作为辅助判断。

不要因为标题相同就跨项目或跨分支合并。不要把别人的 merge commit 仅因为出现在自己的 Push 事件中就算作个人功能提交；应核对 author、committer 和实际变更。

## push -f 和重复提交处理

push -f 可能让同一逻辑修改出现多个 SHA。报告面向工作内容时，应识别逻辑工作项，而不是机械地逐 SHA 罗列。

建议使用以下判断顺序：

1. 同一项目、同一分支、同一 MR。
2. 标题和正文表达的是同一问题。
3. 变更文件集合高度重合，或后一个提交明显是前一个提交的修正、补充、格式调整。
4. 时间上后一个提交是该分支最终保留的提交。

满足上述条件时，只保留最终提交或最终工作结果。不能只按短 SHA 去重，也不能只按标题去重。跨项目的同名移植、同一功能在多个仓库的配套提交，应保留为不同项目工作项，但可以在正文中说明它们属于同一功能。

“过程性提交”“WIP”“fixup”“amend”通常不单独形成工作项，除非它们本身解决了独立问题或用户明确要求逐笔列出。

去重是内部整理动作。除非用户要求，不在报告中增加“去重说明”“排除说明”或解释性尾注。

## Markdown 报告格式

### 标题和概览

报告标题使用用户指定的日期范围，例如：

2026年8月14日至9月8日工作回顾

概览可包含：

- 用户账号。
- GitLab 地址。
- 统计范围。
- 展示时区。
- 主要工作项数量。
- 关联合并请求数量。

不自动加入“设备验证未完成”“数据仅依据元数据”等免责声明。只有用户要求或确实影响结论时，才在对应工作项中说明验证状态。

### 工作总表

建议字段：

| 时间 | 项目 | 分支 | 提交或 MR | 标题 |
|---|---|---|---|---|

提交和 MR 使用 GitLab 链接，时间统一为用户指定时区。

### 详细工作项

每笔主要工作至少包含：

- 项目/时间
- 分支
- 提交标题或 MR 标题
- 问题点
- 解决方案
- 关键文件

问题点和解决方案应说明实际改动解决了什么，不要只重复 Commit 标题。关键文件优先列出实际变更文件；文件较多时列出主要文件，并注明变更文件总数。

### 排版要求

如果用户提出排版要求，严格按用户要求执行。例如：

- 各级标题之间保留三个空行。
- 不使用反引号包裹正文内容。
- Summary、Notes 和正文统一使用中文。
- 不增加用户没有要求的章节、免责声明或 AI 式总结。
- 标题、表头、字段顺序以用户提供的参考文档为准。

如果用户未指定，使用简洁的中文 Markdown，不堆叠装饰，不生成无法在 Typora 或企业微信中正常显示的复杂语法。

## 输出和文件管理

默认只在用户指定目录生成最终 Markdown。原始 API 响应可以写入临时目录，完成后删除或留在系统临时目录；除非用户明确要求，不要把原始 HTML、JSON、CSV、截图和调试脚本混入交付目录。

生成前检查目标目录是否已有同名文件。已有文件时先询问覆盖、另存为还是更新；不要静默覆盖用户的历史报告。

文件完成后检查：

- 文件名符合用户要求。
- Markdown 标题、表格和链接可被 Typora 解析。
- 时间范围和时区一致。
- 每笔详细工作都包含项目、时间、问题点、解决方案和关键文件。
- 主表和详细章节的 Commit/MR 标识一致。
- 没有 Token、Cookie、密码或调试信息。
- 没有无意义的 HTML、JSON、CSV 和临时文件混入交付目录。

## API 不可用时的回退

只有在 API 因权限、版本或网络原因不可用时，才使用用户已登录的 GitLab 浏览器页面作为回退。

回退时：

- 复用用户当前已登录页面，不导出 Cookie。
- 通过个人活动页面的分页或无限滚动加载完整时间范围。
- 从活动项读取时间、项目、分支、Commit 和 MR 链接。
- 仍然按 UTC 和用户时区转换后过滤。
- 仍然执行 Commit/MR 关联和 push -f 重复工作项整理。

如果浏览器页面和 API 结果冲突，先说明差异并确认 GitLab 版本、权限、时间字段和分页边界；不能静默选择看起来数量更多的一侧。

## 常见错误

| 问题 | 处理 |
|---|---|
| API 返回 401 | 检查 Token 是否为空、过期、路径错误或未传 Header；向用户确认 Token 位置和权限 |
| API 返回 403 | 检查 Token scope、项目可见性和用户权限 |
| API 返回 200 但没有个人数据 | 确认请求是否带认证 Header，检查返回用户和分页参数 |
| 只统计到最近少量记录 | 检查 page、per_page、after、before 和排序；不要把 Atom 当完整数据源 |
| Push 数量和 Commit 数量不同 | 一个 Push 可以包含多个 Commit，分别统计事件和提交 |
| MR closed 被写成已合并 | 读取 merged_at 和 merged_by 后再判断 |
| 报告出现大量重复 SHA | 先按项目、分支、MR、标题和变更文件识别 push -f 产生的同一工作项 |
| Typora 或企业微信排版异常 | 使用普通 Markdown 表格和列表，减少复杂嵌套语法，按用户要求处理空行和反引号 |
| 交付目录出现大量网页文件 | 将原始抓取结果放临时目录，最终目录只保留 Markdown |
