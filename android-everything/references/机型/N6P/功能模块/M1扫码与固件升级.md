### V2.4.70 Slave 文本记录与 UART 传输单位

对 `D:\xgd\n6p\cyx-n6p-support-upgrade-m1\升级方式\固件\V2.4.70.0.0_UART\01\1Slave_Double_BGA49_GPIO.txt` 的只读统计显示：文件有 3812 个物理文本行，其中 21 个空行、7 个 `#` 注释行，余下 3784 行均为有效偶数长度十六进制记录。当前 Recovery 的 `M1TransferFirmware()` 跳过空行和注释；`M1ParseFrame()` 将每两个十六进制字符转换为一个 `uint8_t`，校验起始字节 `0x5A`、末尾 `0xA5` 和 BCC。因此文本字符本身不会以 ASCII `5`、`A`、`0`、`0` 的形式发送到 UART。

该 Slave 文件的 3784 条记录全部满足“第 4、5 个二进制字节组成的长度值 + 7 = 整条二进制帧字节数”，且均通过当前 Recovery BCC 算法校验。按二进制帧字节数分组为：13 字节 8 条（命令 `0x2E`、声明 payload 6 字节）、27 字节 1 条（`0x20`、20 字节）、99 字节 1 条（`0x30`、92 字节）、139 字节 3760 条（`0x58`、132 字节）、141 字节 14 条（`0x30`、134 字节）。主流 139 字节记录在 8N1、115200 bit/s 下的纯线路传输下限约为 12.066 ms；这不含 `tcdrain()` 调度、模块处理和逐条 ACK 等待。

Recovery 的“逐条发送”是协议级概念：每条有效记录解析为一个二进制帧，`M1WriteAll()` 会在发生短写时重复 `write()` 直到整帧进入 TTY 输出队列，再调用 `tcdrain()` 等待发送队列排空，随后等待该记录的串口回复。一个 POSIX `write()`、UART FIFO 取数和一次 `read()` 都不是固件记录边界；例如 16 字节硬件 FIFO 只意味着 139 字节帧在发送中会被驱动分多次填入 FIFO，不会把它变成 9 条 M1 升级记录。

### A13 `/private2` 的 native 库加载边界

本节仅说明 Android 正常系统的 A13 代码路径；A12 Recovery 的源码和 SELinux 规则不能作为本节的运行时依据。

`A13/frameworks/base/services/core/java/com/android/server/pm/InitAppsHelper.java` 将 `/private2/app` 按 `PARSE_IS_SYSTEM_DIR`、`SCAN_AS_SYSTEM` 扫描，并将 `/private2/priv-app` 额外按 `SCAN_AS_PRIVILEGED` 扫描。因此，未被 `/data` 更新覆盖的 `/private2` APK 是 bundled system app。`PackageAbiHelperImpl` 的标准 ABI 推导仍不是平铺库目录：目录型 cluster package 的正式目录是 `<codePath>/lib/<instruction-set>`；单 APK bundled package 的正式目录是 `/private2/lib64/<apk-name>/`（64 位示例）。这个“正式 nativeLibraryDir”与本树额外加入的实际搜索目录必须区分。

N6P A13 在三个位置对 `/private2` 做了非上游 AOSP 的定制：

1. `LoadedApk.makePaths()` 先加入 `ApplicationInfo.nativeLibraryDir`，再加入 `base.apk!/lib/<primaryCpuAbi>`。`DexPathList.getAllNativeLibraryDirectories()` 发现库路径含 `/private2/` 且含以 `/arm64-v8a` 结尾的 ABI 路径时，会将 `/private2/lib64` 插入 native 搜索列表最前面；32 位则插入 `/private2/lib`。
2. `DexPathList.findLibrary()` 按列表顺序查找 `System.mapLibraryName()` 得到的文件名，找到第一个可读普通文件即返回。因此，对 64 位 `/private2` APK 的 `System.loadLibrary("SerialPort")`，若存在 `/private2/lib64/libSerialPort.so`，该平铺文件会先于 APK 内的 `lib/arm64-v8a/libSerialPort.so` 被选中。此机制是“调用 `System.loadLibrary()` 时按名称查找”，不是开机预加载目录中所有 `.so`。
3. `art/libnativeloader/library_namespaces.cpp` 对 dex path 正则 `(^|:)/private2/` 同时把 `/private2/lib64` 加到 app linker namespace 的 `library_path` 和 `permitted_path`；bionic 的 shared namespace 创建也补入同一路径。故此树不只是 Java 层找到平铺库，也为 linker namespace 放行该目录。

调用的精确交接顺序为：应用类的静态初始化调用 `System.loadLibrary("SerialPort")`；`System.java` 取得调用类，交给 `Runtime.loadLibrary0()`；后者通过该类所属的 `ClassLoader.findLibrary("SerialPort")` 取得具体文件名，再以“具体文件路径 + 原 ClassLoader”调用 native `nativeLoad()`。`System.mapLibraryName()` 将逻辑名转换为平台文件名 `libSerialPort.so`。因此 `System.loadLibrary()` 不接受路径，也不会自行预加载任意 `.so`；它是一次按逻辑名、在调用 APK 自己的搜索列表中定位并加载库的请求。

`DexPathList.findNativeLibrary()` 对目录元素检查 `<目录>/<lib文件名>` 是否可读；对 APK ZIP 元素仅接受未压缩的 `lib/<ABI>/<lib文件名>` 条目，并返回 `APK!/lib/...` 形式的伪路径。随后 `nativeLoad()` 选择这个 ClassLoader 关联的 namespace，bionic linker 再执行实际 `dlopen`：检查 namespace、SELinux 和 ELF 格式，映射库的代码/数据段，解析其依赖库与符号，并在存在时调用 `JNI_OnLoad`。任一步失败都会使 `System.loadLibrary()` 抛出 `UnsatisfiedLinkError`；在类静态初始化中发生时，类不能完成初始化。

`file_contexts` 只为 `/private2/lib` 定义了 `private_lib`，没有为 `/private2/lib64` 定义专用标签，所以 `/private2/lib64/*` 的源码预期标签是上层通配规则的 `persist_file`。A13 供应商策略明确给 `system_app` 与 `priv_app` 对 `persist_file:file` 的 `open`、`read`、`map`、`execute` 权限。只从源码看，`/private2/lib64` 是为 64 位私有系统/特权 APK 准备的平铺加载目录；实际设备仍须以 `ls -Z`、`ps -AZ`、`logcat` 和 AVC 确认刷入镜像的标签、进程域和编译后的策略一致。

### `n6pro_custom_Pavo_signed` 与 `n6pro_custom_Yoco_signed`

2026-08-04 只读检查表明，Pavo 的 `updater-script` 只解压 `custom -> /private2/custom` 与 `priv-app -> /private2/priv-app`，没有解压 ZIP 顶层的 `app/`、`lib/` 或 `lib64/`。因此 Pavo ZIP 中的顶层 `lib64/libnative-lib.so` 不会因该脚本部署到设备，不能成为上述 A13 平铺加载机制的证据或修复。

Yoco 的 `updater-script` 则先 `delete_recursive("/private2/")`，再显式解压 `lib64 -> /private2/lib64`，同时部署其 `/private2/app` 与 `/private2/priv-app` APK。其顶层有 25 个平铺 arm64 库，均与 yoco manager/payments APK 内的库内容相同。结合本节确认的 A13 `DexPathList`、`libnativeloader`、bionic 和 SELinux 源码，Yoco 的平铺 `lib64` 是与 N6P A13 私有 APK 64 位加载定制相匹配的部署布局，而不是标准 `PackageAbiHelper` 推导的每 APK 子目录布局。

Yoco 的包内容和交付说明不能替代真机运行结论。它还会递归删除整个 `/private2`，测试时必须将其视为破坏性 OTA；要证明某个 Yoco APK 实际使用了平铺库，仍需同一版本设备上的 `pm path`、`dumpsys package`、`ps -AZ`、`ls -Z /private2/lib64`、应用日志和 AVC。

## Recovery 集成边界

Recovery 的传统 ZIP 从包内提取并执行 `update-binary`，私有 edify 函数由该二进制提供。详细源码位置见 `专题/Recovery与OTA.md`。

因此，若 M1 包调用新增或扩展的私有 edify 行为，该行为必须编译进该包携带的 `update-binary`；仅修改父 Recovery 安装器不能改变旧包内二进制支持的函数集合。

### 根因链

Android 的 `GeneralDdi.ddi_device_poweron()` 虽然同样使用命令号 `0x0003` 和单字节 `0x01`，但 JNI 不会直接将其转发给安全处理器：

1. `Ddi.ddi_general_interface()` 的 JNI 实现调用 `ddi_general_interface()`。
2. `ddi_general_interface()` 对 `0x0003` 进行本地分派，调用 `ddi_devices_operate(lParam[0])`。
3. N6 的 `ddi_device_poweron()` 直接向 `/proc/nexgo/scan_pwr` 写入 `1`；`ddi_device_poweroff()` 写入 `0`。同一实现中的 `ddi_device_ctrl_set()` 与 `ddi_device_ctrl_clear()` 当前直接返回 `0`，不执行硬件写入。
4. 当前 Recovery 代码绕过了这层本地分派，直接调用 `wrapper_spi_ddi_general_interface()`，该函数把 `0x0003` 封装成 SPI 请求发送给安全处理器。真机日志证明安全处理器返回了 `14`。

因此，已确认的根因是 **旧 Recovery M1 代码误把 Android 本地 GPIO 控制命令当作安全处理器 SPI 命令转发**。源码未找到安全处理器返回值 `14` 的语义定义，不能把它进一步命名为某一种具体硬件错误。

### 2026-08-05 Recovery 内连续升级入口调整

当前未提交的 `A12/bootable/recovery/xgdrecovery/install.cpp` 已将入口改为“探测优先、上电兜底一次”，取代此前每轮入口都写 `scan_pwr=1` 的行为。该变更只完成源码和静态 diff 核验，尚未编译或真机验证。

1. 完成 OTA 固件文本与清单预校验后，直接打开 `/dev/ttyS1`，以 115200 发送 BootLoader probe。
2. 若 probe 收到现有代码认可的 BootLoader 回复，直接开始 Master 下传；如果需发送 `BootLoaderPrepare`，发送后同样进入下传。
3. 只有 probe 的结果是 `serial response timeout` 时，才关闭并以 9600 重开串口，发送 `S_CMD_020D` 请求命令模式；收到 payload `90 00` 后发送进入 BootLoader 命令、等待 1 秒、切回 115200，再开始 Master 下传。
4. 只有上述两个协议探测都超时，才显示 “no response; retrying after power on”，向 `/proc/nexgo/scan_pwr` 写 `1`、等待 2 秒，并从 BootLoader probe 起完整重试一次。
5. 收到无法识别的 probe 回复、命令模式非 `90 00` 回复、串口断连、读写失败，都会直接失败；第二次探测仍双超时也会失败。它们不会触发反复上电。

#### `upgrade.ini` 的解析与当前串口配置边界

2026-08-18 对两个交付 OTA 包的 `m1/upgrade.ini` 和对应源码核验：它们仍是历史 M1 清单内容；当前预研版本继续使用 `format_version=1`，但固件条目不再增加通用 `role`，并在 `[Task1.Params]` 中声明 `master_path`、`master_reset_path`、`slave_path`、`slave_reset_path`。`size` 与 `sha256` 校验的是包内固件文本文件本身，不是解析后单条 UART 帧的长度。

### 2026-08-27 `package_extract_dir` 原生覆盖行为修正

前一版实现曾误把缓存清理和缺少 ZIP 目录检查加入 `package_extract_dir()`，现已全部撤回。当前 `package_extract_dir()` 保持原有实现：对同名文件使用覆盖写入，但不清空目标目录，也不主动检查源目录是否存在。

最终脚本只保留：

```edify
package_extract_dir("m1", "/cache/m1");
PeripheralUpgrade("/cache/m1");
```

`PeripheralUpgrade()` 的 C++ 接口返回 `INSTALL_SUCCESS` 或 `INSTALL_ERROR`；可选外设目录不存在时记录 `event=skipped|reason=directory_missing` 并返回 `INSTALL_SUCCESS`，Driver 不存在、M1 文件或协议失败、以及升级结束清理失败返回 `INSTALL_ERROR`，edify 包装层只将非成功结果转换为 `ErrorAbort()`。正常进入框架后，升级结束前会清理 `/cache/m1`；升级前不由脚本额外删除目录。

由于原生 `package_extract_dir()` 不清空目标目录，正常升级依赖框架上一次成功或普通失败返回时已经清理 `/cache/m1`。若进程被强制杀死或设备断电，可能残留缓存目录；下一次没有 `m1/` 的 OTA 无法仅凭 `PeripheralUpgrade("/cache/m1")` 区分“本次未打包”与“上次残留”，这是当前不修改 `package_extract_dir()`、不增加清理脚本前提下的已知边界。

### 2026-08-18 框架版首次真机 sideload 失败

状态：已确认首个失败点；尚未修改源码或重新构建。  
设备证据：N6Pro 处于 Recovery、SELinux `Enforcing`。实际执行的 `/tmp/update-binary` SHA-256 为 `15b40cd4343badd129a9d7bd1862456db8cf67162e656acdf039916fb561f099`，与本轮构建和交付 OTA 相同。

本次 V2.4.70 OTA 的 `[Task1.DriverConfig]` 为 `serial_device=/dev/ttyS1`。设备上的 `/dev/ttyS1` 存在，类型为字符设备，主次设备号为 `4:65`，标签为 `u:object_r:ttyS_device:s0`；`/dev/ttyMT1` 不存在。因此“`/dev/ttyS1 is not a character device`”不是清单填写错误或设备节点实际类型错误。

失败发生在 `PeripheralUpgrade` 的 Driver `Validate()` 阶段。新代码调用 `lstat(serial_device)` 后检查 `S_ISCHR()`；内核同期记录 `update-binary` 的 AVC：`recovery` 域被拒绝对 `/dev/ttyS1` 执行 `chr_file getattr`。当前 `recovery.te` 对 `ttyS_device` 只有 `{ ioctl open read write }`，没有 `getattr`。`lstat()` 因 AVC 失败后，当前代码把“系统调用失败”和“节点类型不匹配”合并成同一条错误文案，因而出现误导性提示。

本轮尚未进入 M1 上电、串口 `open()`、BootLoader probe 或固件下传；没有生成任务 state/trace，`/tmp/m1` 已按受控失败路径清理。最小后续修复是仅为 `recovery` 域、`ttyS_device:chr_file` 增加 `getattr`，同时可将 `lstat()` 的 `errno` 单独打印，便于将权限错误与实际路径/类型错误区分开。该修复需重新构建 Recovery 镜像后再验证。
